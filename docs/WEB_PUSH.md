# الإشعارات (Web Push) — الإعداد والقيود

## لماذا Web Push القياسي (VAPID) وليس Firebase؟

| | Web Push + VAPID (المستخدم) | Firebase Cloud Messaging Web SDK |
|---|---|---|
| حساب خارجي | لا يحتاج | يحتاج مشروع Firebase وإعدادات |
| Chrome / Edge / Android | ✓ (يمر عبر FCM تلقائيًا) | ✓ |
| Firefox | ✓ | ✓ |
| Safari / iPhone (PWA مثبت، iOS 16.4+) | ✓ | ✓ (عبر نفس معيار Web Push) |
| الأسرار | مفتاح VAPID خاص في متغيرات الخادم | Service account + إعدادات الويب |

Chrome على Android يستخدم FCM داخليًا مع Web Push القياسي، فلا نحتاج Firebase SDK. هذا أبسط وأكثر استقرارًا وأقل اعتمادًا على جهات خارجية.

## الإعداد (مرة واحدة)

```bash
cd backend
npm run vapid:generate
```

انسخ الناتج إلى متغيرات البيئة (محليًا في `backend/.env`، وعلى Railway في Variables):

```
VAPID_PUBLIC_KEY=<Public Key>
VAPID_PRIVATE_KEY=<Private Key>
VAPID_SUBJECT=mailto:it@your-company.com
```

- **لا تغيّر المفاتيح بعد التشغيل**، فتغييرها يبطل اشتراكات كل الأجهزة (سيعيد كل عامل تفعيل الإشعارات).
- المفتاح العام يُرسل للمتصفح عبر `GET /api/push/status`. المفتاح الخاص لا يغادر الخادم.
- بدون المفاتيح يعمل النظام بالكامل لكن بدون إشعارات، وتُسجل الإشعارات `SKIPPED (PUSH_DISABLED)`.

## خطوات العامل (مرة واحدة على هاتفه)

1. يفتح رابط النظام (HTTPS) ويسجل الدخول.
2. **يثبت التطبيق**: Android/Chrome عبر زر «تثبيت التطبيق» أو قائمة المتصفح، وiPhone عبر Safari ← مشاركة ← «إضافة إلى الشاشة الرئيسية» (**إلزامي على iPhone لاستقبال الإشعارات**).
3. يضغط «تفعيل الإشعارات» ويوافق.
4. يجرّب «تجربة الصوت والاهتزاز» من صفحة الحساب.
5. (Android) يُنصح بإعدادات الهاتف ← التطبيقات ← المتصفح/التطبيق: السماح بالإشعارات بأولوية عالية وإيقاف «تحسين البطارية» للمتصفح.

يظهر في صفحة العمال للمدير لكل عامل: الجهاز المرتبط، وهل الإشعارات مفعلة، وآخر اتصال.

## ماذا يفعل النظام عند وصول طلب

| الحالة | السلوك |
|---|---|
| التطبيق مفتوح وظاهر | إشعار من الـService Worker + شريط «طلب جديد» داخل التطبيق + **صوت واهتزاز يتكرران كل 6 ثوانٍ** حتى يفتح العامل الطلب |
| في الخلفية أو مغلق | إشعار نظام مستقل لكل طلب: العنوان «طلب جديد من المدير …»، النص عنوان الطلب، اهتزاز طويل متكرر النمط، يبقى ظاهرًا (`requireInteraction`). النقر يفتح الطلب نفسه |
| لم يُفتح خلال 5 دقائق | تذكير يعيد تنبيه الإشعار (حتى 3 مرات) |
| تعديل / إلغاء / إعادة فتح | إشعار «تم تعديل الطلب» / «تم إلغاء الطلب» (يزيل إشعار الطلب) / «تمت إعادة فتح الطلب» |
| الهاتف بدون إنترنت | خدمة الـPush تحتفظ بالإشعار حتى 24 ساعة (`notifications.ttlSeconds`)، والطلب نفسه محفوظ على الخادم ويظهر عند المزامنة |

## القيود التقنية الحقيقية (لا يمكن تجاوزها من PWA)

هذه قيود يفرضها نظام التشغيل والمتصفح على أي تطبيق ويب، **والنظام لا يحاول التحايل عليها**:

1. **الصوت المخصص للإشعار غير مدعوم في المتصفحات**: خيار `sound` في Notification API لا يطبقه أي متصفح رئيسي. إشعار النظام يستخدم **صوت الإشعارات الافتراضي** للهاتف. الصوت المخصص (`/sounds/alert.wav`) يعمل **داخل التطبيق عندما يكون مفتوحًا** فقط.
2. **التنبيه المتكرر عندما يكون التطبيق مغلقًا**: لا يستطيع الـPWA تشغيل صوت أو اهتزاز مستمر في الخلفية. البديل الرسمي المستخدم: نمط اهتزاز طويل + إشعار يبقى ظاهرًا + تذكير كل 5 دقائق.
3. **الوضع الصامت / عدم الإزعاج (DND)**: يحددهما المستخدم ونظام التشغيل. على الوضع الصامت لا يُشغل صوت (وقد يبقى الاهتزاز حسب إعداد الهاتف)، وفي «عدم الإزعاج» قد تُخفى الإشعارات تمامًا. لا توجد API ويب لتجاوزهما. يمكن للعامل إضافة المتصفح أو التطبيق إلى استثناءات «عدم الإزعاج» من إعدادات الهاتف.
4. **iPhone / iOS**:
   - الإشعارات تعمل **فقط** بعد تثبيت التطبيق على الشاشة الرئيسية (iOS 16.4 أو أحدث).
   - **لا يوجد اهتزاز** من الويب (Vibration API غير مدعومة في Safari).
   - `requireInteraction` غير مدعوم، فالإشعار يختفي من الشاشة حسب سلوك iOS ويبقى في مركز الإشعارات.
   - Background Sync غير مدعوم، فالمزامنة تتم عند فتح التطبيق أو عند عودة الإنترنت أثناء فتحه.
5. **Android**: مدّخر البطارية لدى بعض الشركات (Xiaomi، Huawei، Samsung بإعدادات صارمة) قد يؤخر الإشعارات. الحل: إيقاف تحسين البطارية للمتصفح. وإذا أُغلق المتصفح قسرًا (Force stop) فلا تصل الإشعارات حتى يُفتح مجددًا.
6. **الصوت والاهتزاز داخل التطبيق** يحتاجان تفاعلًا واحدًا من المستخدم مع الصفحة بعد فتحها (سياسة autoplay). أي لمسة (مثل إدخال الـPIN) تكفي.
7. **«متصل» عند إغلاق التطبيق**: لا يوجد عمل خلفي دوري في الـPWA، لذلك يظهر العامل «غير متصل» عند إغلاق التطبيق مع أن الإشعارات ما زالت تصله. حالة الإشعار في صفحة الطلب («وصل للجهاز») تؤكد الاستلام الفعلي.
8. **تأكيد التسليم** (`DELIVERED`) يُرسله الـService Worker عند وصول الإشعار. إذا كان الهاتف بلا إنترنت لحظتها يبقى `SENT`.

## ما تم التحقق منه آليًا

- اشتراك Push حقيقي من Chrome لدى خدمة FCM، وقبول FCM لإشعار مشفر وموقع بـVAPID (HTTP 201) بنفس المكتبة التي يستخدمها الخادم.
- معالجة ردود خدمة الـPush (201 / 404 / 410 / 429 / 5xx)، وتنظيف الاشتراكات، وإعادة المحاولة، والتذكير — اختبارات الـbackend.
- **يجب التحقق يدويًا على هاتف حقيقي** من ظهور الإشعار والصوت والاهتزاز. قائمة الفحص في [TESTING.md](TESTING.md#فحص-يدوي-على-الهواتف).
